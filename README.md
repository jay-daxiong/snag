# Snag 原型 · 使用与对接说明

## 怎么跑起来

需要 Node（本机已装 v22）。在 `snag` 目录下：

```
node server.js
```

然后打开：

- 前端 App：<http://127.0.0.1:8787>
- 数据后台：<http://127.0.0.1:8787/admin>（需要管理员登录：默认账号 `admin` / 密码 `admin123`，可用环境变量 `SNAG_ADMIN_USER` / `SNAG_ADMIN_PASS` 覆盖；生产务必修改并改用 HTTPS）

停止服务：Ctrl+C。数据写在 `server-data.json`，删掉它就会重新生成一套演示数据。

**不启动服务也能看**：直接双击 `index.html` 也能用，界面会自动降级到本地模拟（验证码直接显示、订单走本地存储），只是后台看板没数据。

## 哪些是真的，哪些是模拟的

这一版必须说清楚，别误以为已经能上线。

### 真能用的

- **一键定位（全国精准，双保险）**：调用浏览器原生 Geolocation 拿到真实经纬度后分两层——
  1. **离线层**（`regions.js` 逆向编码，自带 2845 个区/县坐标）：立即、必然精准到**省·市·县**三级，断网也生效；算法取全局最近区县（≤80km 才下钻并据此定省/市），绝不会把直辖市、省界附近的坐标错配到邻省。
  2. **在线层**（`geocode.js`）：联网时再调用 BigDataCloud / Nominatim 反向地理编码，把定位补齐到**全国任意区/县**（已实测：上海→黄浦区、北京→东城区、桐乡→桐乡市）。接口不可达时静默退回离线结果，不阻塞主流程。
  - 浏览器拒绝授权或不支持时，城市抽屉里可以手动按「省 → 市 → 区/县」三级联动选到全国任意区县；联网时若未手选具体县，也会自动补齐区/县。
- **身份证校验**：用的是 GB 11643-1999 的 mod 11-2 校验位算法，这是国家标准算法，能挡住随手编的号码。
- **手机号 / 邮箱格式校验**：真实正则。
- **登录即注册**：服务端签发令牌，前后端分离，未登录访问会返回 401。
- **同城数据**：覆盖**全国 34 省 · 345 个地级市**，每座城市各自独立的数据集，切换会重新加载；选定区/县后，同城搜索会优先匹配该区。
- **所有智能能力**：抢手指数、摘要抽取、风险识别、意图搜索、推荐、路线规划，逻辑都是真的，只是用的是确定性规则而不是训练模型。

### 模拟的（需要换真服务）

下面三项是**交付标准**：代码已经是生产形态（真签名 / 真验签），只是缺密钥时自动降级为演示，**接口形状完全一致**，部署时填好环境变量即可切换为真服务，**不用改任何调用方代码**。

| 环节 | 现在怎么做（演示模式） | 真上线要做什么（填环境变量即可） |
| --- | --- | --- |
| 短信验证码 | `sms.js` 生成 6 位码并直接在响应返回（演示）；`SNAG_SMS_PROVIDER=aliyun` 默认 | 配置 `SNAG_SMS_ALIYUN_*` 或腾讯云 `SNAG_SMS_TENCENT_*`，`sms.js` 会用 **HMAC-SHA1（阿里云 v1）/ TC3-HMAC-SHA256（腾讯云）** 真实签名发送；服务端**不再把验证码回传前端**，并加 60s 频率限制 |
| 邮箱验证码 | 同上，没真发邮件 | 接邮件服务（如 SendGrid、阿里云邮件推送），发一封带验证码的邮件 |
| 支付 | 本地生成订单号，演示二维码 + "模拟支付"回调 | 配置微信支付 V3（`SNAG_WX_*`：商户号 / APIv3 密钥 / 证书）或支付宝（`SNAG_ALI_*`），`pay.js` 会做 **RSA-SHA256 下单 + AES-256-GCM 回调解密 / 支付宝 RSA2 验签**；支付平台异步回调 `/api/pay/notify` 已做验签，订单状态以后台通知为准 |
| 实名认证 | 只做格式与校验位检查，提交后进待审队列，后台人工点通过/驳回 | 接第三方实名服务（如阿里云实人认证、微信支付实名），需要营业执照和对公账户，涉及个人敏感信息要过合规 |
| 后台权限 | 已加管理员登录鉴权（Bearer Token，未授权返回 401）；并支持 **admin / moderator 双角色**与**操作审计日志**（`db.audit` 记录登录/审核/下架/封禁/通过/注销），moderator 仅能看内容/实名/举报面板 | 生产仍需改用 HTTPS（已支持读证书自动启用），并建议接入后台自助账号管理 UI |

> 演示模式的设计目的：本地零配置即可把**整条链路**跑通验收（注册→实名→支付→审核→增长→注销），真上线只是把环境变量填实，行为不变。

## 本版新增能力（面向上架与增长）

围绕「让更多人愿意把闲置上架、并通过裂变带来新用户交易」做了四类增强，均已通过自动化测试。

### 1. AI 智能客服
- 后端 `ai.js`：OpenAI 兼容的 LLM 代理（默认指向本地 OFM 免费网关 `http://127.0.0.1:18900/v1`），携带 Snag 领域知识的系统提示词；**模型不可达时自动回退到规则 FAQ**（10 组关键词意图，覆盖发布、交易、支付、实名、安全等高频问题），保证永远有应答。
- 前端 `aiwidget.js`：右下角浮窗，预置快捷问题（怎么发布、见面交易安全吗、怎么退款…）+ 自由提问，回答流式追加到对话区。

### 2. 发布闲置 + 邀请裂变（让用户愿意上架、并带来新用户）
- **发布闲置**：`growth.js` 提供发布表单（标题/品类/成色/描述/地址），写入后端 `/api/listings`，可在「我的发布」下架。
- **邀请裂变**：每个用户有专属 `inviteCode`；好友用邀请码注册，邀请人得 **7 天会员权益**（`INVITE_REWARD_DAYS`），权益可兑换会员；前端生成**分享海报**（含二维码，`qrcode.js` 零依赖生成，已结构校验）。
- **社交证明**：首页展示「附近正在送出 / 本周被领走」等激励数据（`/api/social`），降低发布心理门槛。
- **举报**：对任意闲置可一键举报，后端入队、后台审核。

### 3. 内容审核后台（应用商店合规必需）
- 后台新增「举报审核 / 内容管理」面板：`/api/admin/reports` 列出举报，**一键下架违规闲置**（`/api/admin/takedown`，下架后自动从公开列表消失并标记关联举报已处理）或**封禁违规用户**（`/api/admin/user/ban`，封禁后其闲置统一下架、且无法再登录）。
- 用户表支持封禁/解封操作与状态标识。

### 4. 账号注销 + 隐私/协议 + PWA（应用商店硬性要求）
- **账号注销**：「我的 → 账号管理 → 注销账号」二次确认后调用 `POST /api/account/delete`，撤销令牌、删除账号主体、撤回实名记录、下架名下闲置、清理关联举报——满足 Apple/Google「用户必须能删除账号」的要求。
- **隐私政策 / 用户协议**：`privacy.html` / `agreement.html`，覆盖信息收集、共享、用户权利、未成年人保护、免责等上架披露项；登录卡与「我的」均设入口。
- **PWA 可安装**：`manifest.json` + 生成图标（`icon-192.png`/`icon-512.png`/`icon.svg`），`index.html` 注入 `theme-color`、`manifest` 与 `apple-touch-icon`，可作为可安装 Web App 上架。

### 5. 内容机审 + 多角色后台 + HTTPS 接入（上架合规加固）

- **内容机审前置**：`moderation.js` 在 `POST /api/listings` 发布前自动分级过滤——命中违禁/诈骗/色情词**直接拒绝发布**；命中引流/外联（如"加我微信""留手机号/外链"）**转入 `pending_review` 待人工复核**，不立即公开并自动生成一条机审举报。后台新增「内容机审 · 待复核」面板，可一键「通过并上架」或「下架」。量大时可接入云厂商内容安全 API（已预留 `SNAG_MOD_API` 扩展点）。
- **多角色 + 操作审计**：后台支持两类账号——`admin`（全权，含用户/数据/来源面板）与 `moderator`（仅内容/实名/举报审核，看不到用户与数据面板，网关对敏感接口返回 403）。所有关键后台动作（登录、实名审核、下架、封禁、通过、注销）写入 `db.audit` 操作审计日志，后台「操作审计日志」面板可查，满足合规追溯。
- **HTTPS 接入**：`server.js` 读取 `SNAG_TLS_CRT` / `SNAG_TLS_KEY`（可选 `SNAG_TLS_CA`）后**自动用 HTTPS 启动**，否则回退 HTTP。拿到 Let's Encrypt 或云厂商免费证书，把路径填进 `.env` 重启即生效，无需改代码。

> 上架前还需补齐的资质与配置，见仓库根目录的 `FUNCTIONAL_AUDIT.md`（功能完整性审计 + 上线前清单）。对"从零起步、暂无公司/域名/服务器"的开发者，另见 `LAUNCH_GUIDE.md`（注册公司→备案→申请密钥→HTTPS→部署→上架的全步骤指引）。

### 还要提醒的

- 后台看板里的用户和订单，**一部分是首次启动时预置的演示数据**，另一部分是你在 App 里真实操作产生的。看趋势图时心里有数。
- 物品数据全部是本地生成的，不是抓来的。真产品的数据源合规问题（平台授权、爬虫协议、用户隐私）在《App 右侧说明》里也写了。
- 地图底图是示意性的几何图形，不是真实地理数据；物品坐标是按城市中心随机散布的。

## 功能该放 / 可放 / 不可放 —— 数据驱动决策

后台「功能使用分析 · 数据驱动决策」面板就是用来回答这个问题的。逻辑在 `server.js` 的 `GET /api/admin/analytics`：

1. **埋点采集**：App 里每个关键动作都通过 `api.track(name)` 上报到 `POST /api/track`，落盘到 `server-data.json` 的 `tracks`。
2. **综合评分**：每个功能按 `触达率(adoption) 45% + 使用量(usageShare) 35% + 留存关联(retentionLift) 20%` 算出一个 0–100 的 `score`。
3. **数据自发归类**：`score ≥ 55` 判为核心，≥ 35 为增强，≥ 18 为可选，否则为门槛。这是**纯数据**算出来的，不掺产品主观。
4. **与产品决策比对**：`FEATURE_DEFS` 里是人工 + 经验拍的「该放 / 可放 / 可缓 / 按需」决策，面板把它和「数据自发归类」并排，不一致的项标 **建议复核**（例如「付费墙曝光」「手动选城市」数据上更像增强而非核心）。

也就是说，最终拍板的是产品决策，但数据给出一个可复核的参考——哪些被高频使用且与留存强相关的功能必须保，哪些使用率低可以暂缓，一目了然。接真实数据后，把 `RETENTION_LIFT` 的系数换成回归得到的真实值就行。

## 行政区数据集：权威全量，离线也精准到县

`regions.js` 现在烘焙的是**权威全量行政区划数据**，不再是手写精简版：

- **来源**：阿里 DataV.GeoAtlas 公开行政区划接口（`geo.datav.aliyun.com/areas_v3/bound/{adcode}_full.json`），每个区/县都带 `center:[lng,lat]` 行政中心坐标。
- **覆盖**：34 省 · 345 地级市 · **2842 个区/县**（334/345 个市含真实区县；其余多为直辖市 / 省直辖县级市的特殊处理，仅台北因数据源不服务而回退「市辖区」）。
- **离线精准到县**：`regions.js` 自带逆向编码（`REGION_HELPERS.reverseGeocode`），断网也能把定位精准到**省·市·县**三级；算法先取「全局最近区县」，距离 ≤80km 才下钻并据此确定省/市（避免直辖市、省界附近的坐标错配到邻省），超出则退回最近地级市只保留市级。
- **重新生成**：`node bake_regions.js`（需能访问 DataV；它复用现有省市、补齐全量区县并写回 `regions.js`）。`gen_regions.js` 仍是省市坐标的源头脚本。

**运行时仍保留在线双保险**（`geocode.js`）：联网时再用 BigDataCloud / Nominatim 把定位二次校准到区/县，接口不可达时静默退回离线结果。两者结合——在线极准、离线也准。

`data.js` 会自动用新的 `REGION_HELPERS` 重建城市数据，改完 `regions.js` 重启 `node server.js` 即可，前端无需改动。

## 想接真实支付，改哪里

1. `server.js` 的 `POST /api/pay/create`：换成调用支付平台的下单接口，返回真实的 `codeUrl` 或支付链接。
2. 新增 `POST /api/pay/notify`：接收支付平台回调，**验签**后更新订单状态并开通会员，返回成功回执。
3. `app.js` 的 `openPay()`：把占位二维码换成真实二维码（或直接跳转支付页）。
4. 删掉 `POST /api/pay/mockpay` 和前端的"我已完成支付"按钮。

前端的轮询查询 (`payQuery`) 可以保留，作为回调没及时到达时的兜底。

## 智能引擎怎么换成真模型

`engine.js` 里这三个函数是可以独立替换的，替换后排序和展示逻辑不用动：

- `signals(item)` — 现在用关键词规则抽成色/急出/自提/大件，换成大模型调用即可。
- `parseQuery(q)` — 现在是意图关键词表，换成语义解析或向量召回。
- `summary(item)` — 现在是模板拼接，换成大模型生成一句话。

抢手指数 `hotScore()` 的权重是人工先验值，**上线前应该用历史领取数据回归校准**，否则"预计几小时内被领走"只是个好看的说法，没有真实准确率。
